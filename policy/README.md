# Disclosure policy

[`disclosure-policy.yaml`](disclosure-policy.yaml) decides what each kind of user may see at each
stage of building a cohort, and how counts are protected before they are released. It is data,
not code: the data access committees review and approve it, and every response records the
`policy_version` it was shaped under.

The policy is a **draft**. Values marked `# proposed` or `# pending committee approval` need
committee approval before the policy is used with real data.

## How the pieces fit

| File | Role |
|---|---|
| [`policy/disclosure-policy.yaml`](disclosure-policy.yaml) | The decisions: thresholds, noise, and what each tier may do at each stage |
| [`schema/policy.yaml`](../schema/policy.yaml) | The structure of the policy, what each value means, and the rules a valid policy must follow |
| [`schema/summary.yaml`](../schema/summary.yaml) | The summary response format. It is tier-agnostic: it can carry exact or obfuscated counts |
| [`schema/summary-profiles.yaml`](../schema/summary-profiles.yaml) | The profiles a response must pass for a tier: Totals, Breakdown, Exact Totals and Exact Breakdown. Generated by [`schema/generate_summary_profiles.py`](../schema/generate_summary_profiles.py) |
| [`schema/tests/test_disclosure_policy.py`](../schema/tests/test_disclosure_policy.py) | Validates the policy against its schema, and checks its links to the summary schemas |

The summary schema says what a response *can* contain. A profile says what a response *may*
contain for one view. The policy says which profile each tier gets at each stage, and which
database role (pool) the stage's queries run as. A stage with no profile returns no counts.

The schemas only check structure. Noise, suppression and scope checks are carried out by the
middleware; the policy is the specification it follows.

## Tiers

| | Public | Authenticated | Authorized |
|---|---|---|---|
| Who | Anyone, without signing in | Signed in through NIH RAS | Authenticated, with dbGaP approval for at least one consent group in the release |
| Accountability | None | RAS account | RAS account plus visa IDs |
| Exact counts | Never | Never | Within exact scope: entitled consent groups whose current eligibility allows exact counts |
| Limits | Rate limit: 60 requests per minute per network address | Query budget: 500 units per day per account | Query budget: none within exact scope; other queries draw on the authenticated budget |
| Overlap check | Global, across every set in the fixed table; matches withheld when the table is built | Per account; a matching query is refused | Per account; a matching query is refused |
| Request logging | No | Every request | Every request |
| Retired releases | No | No | Own saved cohorts only |

### Stage by stage

Each cell gives the pool and the profile, then the stage's limits. "No counts" means the stage
has no profile.

| Stage | Public | Authenticated | Authorized |
|---|---|---|---|
| 0 Sign-in and scope | Not available | Sign in; budget assigned | Sign in; exact scope computed from visas and shown up front |
| 1 Search and add terms | `api_search`, no counts. Stigmatizing terms shown, not filterable | `api_search`, no counts. Stigmatizing terms shown, not filterable | `api_search`, no counts. Stigmatizing terms filterable within exact scope, if approved |
| 2 Live summary per term | `api_public` → Totals | `api_public` → Totals | `api_counting` → Exact Totals |
| 3 And, Or and Not | `api_public` → Totals. And only; up to 2 terms, read from the fixed table | `api_counting` → Totals. And, Or, Not; 20 terms; nesting 3 | `api_counting` → Exact Totals. And, Or, Not; 20 terms; nesting 3 |
| 4 Refine criteria | Not available | `api_counting` → Totals. Ranges at least one bin wide; time windows of at least 30 days | `api_counting` → Exact Totals. Range minimums relaxed within exact scope, if agreed; time windows of at least 30 days when reaching outside exact scope, no minimum within it (proposed) |
| 5 Cohort and visuals | Not available | `api_counting` → Breakdown. Obfuscated charts; unreported consent groups listed as below `min_count` | `api_counting` → Exact Breakdown. Exact charts within exact scope, obfuscated outside it |
| 6 Provisioning | No counts. Information on how to request access | No counts. Access request prefilled from the cohort | No counts. A share for eligible groups, an access request for the rest |

`api_public` is a fixed table, built once per release: a summary for every filter of up to two
terms combined with And. Its depth is the `max_terms` of public stage 3, the stage that reads it.
Public users only read the table, never run a live query.

That is what stops them differencing. The table does hold both A and A-and-C, so count(A) minus
count(A and C) is possible within it. But every cell is known before any is released, so
suppression and the overlap check run across the whole table at build time, and any such
difference below `min_count` is withheld before the table is published.

Or, Not, more terms and any refinement need a live query, so authenticated stages 3 and 4 run as
`api_counting`. Their output is still checked against the public Totals profile.

### Limits and the overlap check

Each tier lists its `limits`, each typed by `limit_type`:

- A **rate limit** caps requests per period, as flood protection. It needs only a counter per
  key, so it is the public tier's only limit. A query budget could be added to the public tier
  later; with the fixed table it would add little.
- A **query budget** caps cost-weighted query units per period, as a disclosure control. It
  needs an identity to charge, so only signed-in tiers have one. A tier may draw on another
  tier's budget instead of having its own.

The **overlap check** stops differencing. A released count whose participant set differs from an
earlier released set by 1 to 9 participants (with `min_count` at 10) is not answered with a fresh
count. Every released count is compared, not just each query's cohort. Per account, a match is
refused. Across callers, a refusal would itself reveal that a nearby set was released, so a
global check reuses the earlier answer or withholds the count instead.

### What each profile releases

| Profile | Totals | Per-study counts | `record_count` | Used by |
|---|---|---|---|---|
| `TotalsSummaryResponse` | Obfuscated | None; studies at or above `min_count` are listed without counts | Never | Public and authenticated, stages 2–4 |
| `BreakdownSummaryResponse` | Obfuscated | Obfuscated, per study and consent group, each with a `count_status` | Never | Authenticated, stage 5 |
| `ExactTotalsSummaryResponse` | Exact within exact scope; one obfuscated `outside_scope` figure for the other groups, never added to it | Exact within exact scope; outside it, none: studies at or above `min_count` are listed without counts | Only within exact scope | Authorized, stages 2–4 |
| `ExactBreakdownSummaryResponse` | Exact within exact scope | Exact within exact scope; obfuscated outside it, per study and consent group | Only within exact scope | Authorized, stage 5 |

Approval adds exact counts within the caller's exact scope and nothing else. Outside it, an
authorized user sees what an authenticated user sees at the same stage: Exact Totals matches Totals,
and Exact Breakdown matches Breakdown. Per-group counts outside exact scope come only at stage 5,
on a materialized cohort, for every tier.

Some authorized settings apply only within exact scope: filterable stigmatizing terms, relaxed
ranges, and windows shorter than `temporal_windows.min_days`. A query using any of them is a *relaxed
query*, and it leaves groups outside exact scope out of the response entirely
(`relaxed_queries_outside_scope: EXCLUDED`). There is no out-of-scope figure, no listing of
those studies and no `suppressed_study_count` for them. A relaxed criterion is one an
authenticated user can't use, so even "at least 10 match in that study" would say more than
that user could learn.

The exact profiles are structural only. The middleware must verify the caller's scope before
releasing any exact count.

## How counts are protected

These rules, under `counting`, apply to every tier.

- **Minimum count.** Counts below `min_count` (10) are not reported. `BELOW_MIN_COUNT` means
  "fewer than 10, possibly none", so zero and small counts look alike.
- **Who is counted.** One BDCHM `Participant` is one enrollment, so a person in two studies counts
  twice.
- **Noise.** Obfuscated counts at or above `min_count` get a whole number drawn uniformly from −3
  to +3; a result below `min_count` is shown as `min_count`. The noise is seeded by HMAC-SHA256
  over the release and the matched participants, never the cell's label, so the same participants
  get the same noise wherever they appear. Averaging repeated queries does not remove it.
- **Totals.** A total is the exact union of matched participants across the studies in scope,
  including studies below `min_count`, obfuscated once. It is never a sum of contributions. It is
  exact only if every contributing consent group is in the caller's exact scope. Clients use a
  released total where there is one, and never add up obfuscated counts.
- **Complementary suppression.** Where a parent appears with its parts, the amount a reader could
  work out from the hidden parts must itself be at least `min_count`. Otherwise further parts are
  withheld, smallest first, and if that fails the parent is withheld. Parents include totals over
  their contributions and the cohort total over each facet's values, counting an implied "not
  recorded" part.
- **Releases.** Public and authenticated users query the active release only, and overlap checks
  compare queries across releases.

## Eligibility defaults

The committees decide, for each consent group, whether its participants appear in discovery
counts, whether it can be in an exact scope, and whether its data can be shared at provisioning.
`eligibility` lists suggested starting points for curators, by consent modifier; the committees'
decision per group is what applies.

| Modifier | Discovery counts | Exact counts | Sharing |
|---|---|---|---|
| COL | Allow | Deny | Deny |
| GSO | Review | Deny | Review |
| NPUNCU | Allow | Allow | Review |

Discovery counts as a separate decision is itself proposed.

## Conventions

- **Every stage is written out in full.** Each tier lists all seven stages, and each stage gives
  `available`, `pool` and `profile`. `none` means none, so a missing value is an error, never a
  silent default. An unavailable stage has pool and profile `none` and nothing else.
- **Decisions are fields; meanings are in the schema.** The policy holds values the committees
  can change, such as thresholds, limits and enum choices. What each value means is in the
  descriptions in [`schema/policy.yaml`](../schema/policy.yaml).
- **Versions.** Any change issues a new `policy_version`, including any change to `min_count`.

## What the schema enforces

[`schema/policy.yaml`](../schema/policy.yaml) rejects a policy that would release counts no profile
checks, or that gives a tier more than it should have:

- A stage that returns counts must name a profile; only search may query without one.
- Search never returns counts, and stages 0 and 6 run no queries.
- `api_public` can only produce the Totals profile.
- Public stages can't use `api_counting` and get at most Totals; authenticated stages never get
  either Exact profile.
- Profiles with counts per study and consent group outside exact scope (Breakdown and Exact
  Breakdown) are allowed only at stage 5, for every tier.
- Only the authorized tier has an exact scope.
- The public tier is limited by rate only, per network address, and its overlap check is global
  and never refuses. Every tier has limits; each limit type has its own required fields; a budget
  has its own allowance or draws on another tier's, not both.
- Combining terms reads the fixed table with And only, or runs on `api_counting`; Or and Not
  always need `api_counting`. Refining ranges or allowing time windows also needs
  `api_counting`. Public stages can't use `api_counting`, so public users never get any of these.
- Every tier has exactly seven stages, numbered 0 to 6, and there are exactly three tiers.
- Public stage settings stay locked at the narrowest values even so: And only, no time windows,
  ranges on bin edges only, stigmatizing terms never filterable, and no cohort charts or listings.
- Authenticated stages get no setting that depends on an exact scope (exact charts, relaxed
  ranges, filterable stigmatizing terms, a window minimum within exact scope).
- Time windows are one `temporal_windows` block; a stage without it allows none. Its `min_days` is
  required and governs every query that reaches outside exact scope, for every tier. A shorter
  minimum within exact scope is its own field, `min_days_within_exact_scope`, allowed only for the
  authorized tier.
- The authorized tier must say what a relaxed query returns outside exact scope, and only a tier
  with an exact scope may set it.
- Any stage that combines terms caps how many (`max_terms`); a minimum window needs windows to be
  allowed.
- Noise can't be seeded by anything except the release and the matched participants, and must
  range at least one either side of zero, so it can never be switched off.
- Unknown fields are rejected, so prose can't slip back in as an unchecked field.

The tests also check what LinkML rules cannot express: tier names and stage numbers are unique,
unavailable stages are inert, an approved policy names its noise key (`key_reference`), and every
signed-in tier's limits include a query budget. They also confirm that every profile the policy
names exists in
`summary-profiles.yaml`, and that `identity_rule` is a BDCHM class.

## Changing the policy

1. Edit [`disclosure-policy.yaml`](disclosure-policy.yaml) and increase `policy_version`.
2. Run the tests:

   ```sh
   uv run pytest schema/tests/test_disclosure_policy.py
   ```

   The `identity_rule` test needs BDCHM; run `synthetic/fetch-bdchm.sh` once first.
3. If the change needs a new kind of value, such as a new pool, profile or chart mode, add it to
   [`schema/policy.yaml`](../schema/policy.yaml) with a description of what it means.
4. If the change alters what a profile may contain, update
   [`schema/generate_summary_profiles.py`](../schema/generate_summary_profiles.py) and regenerate
   `summary-profiles.yaml`.

## Open questions

- Subtracting across tiers. Public totals are open to anyone, so an authorized user can subtract
  their exact in-scope count from a public total and recover the out-of-scope remainder to within
  the noise. With one group outside scope, that remainder is a per-group estimate; where it is
  small, it can reveal a count below `min_count`. Closing this needs the remainder rule applied
  across tiers: withhold an exact in-scope cell when the matching public total minus it would
  leave a small remainder.
- The Key Vault key for the noise seed (`key_reference`) is not yet named. The tests will fail if
  the policy is approved without it.
