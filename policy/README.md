# Disclosure policy

[`disclosure-policy.yaml`](disclosure-policy.yaml) decides what each kind of user may see at each
stage of building a cohort, and how counts are protected before they are released. It is data,
not code: the data access committees review and approve it, and every response records the
`policy_version` it was shaped under.

The policy is a **draft**. Values marked `# proposed` or `# pending committee approval` need
committee approval before the policy is used with real data.

## How the pieces fit

| File | Role |
|---|---|
| [`policy/disclosure-policy.yaml`](disclosure-policy.yaml) | The decisions: thresholds, noise, and what each tier may do at each stage |
| [`schema/policy.yaml`](../schema/policy.yaml) | The structure of the policy, what each value means, and the rules a valid policy must follow |
| [`schema/summary.yaml`](../schema/summary.yaml) | The summary response format. It is tier-agnostic: it can carry exact or obfuscated counts |
| [`schema/summary-profiles.yaml`](../schema/summary-profiles.yaml) | The profiles a response must pass for a tier: Totals, Breakdown and Exact. Generated by [`schema/generate_summary_profiles.py`](../schema/generate_summary_profiles.py) |
| [`schema/tests/test_disclosure_policy.py`](../schema/tests/test_disclosure_policy.py) | Validates the policy against its schema, and checks its links to the summary schemas |

The summary schema says what a response *can* contain. A profile says what a response *may*
contain for one view. The policy says which profile each tier gets at each stage, and which
database role (pool) the stage's queries run as. A stage with no profile returns no counts.

The schemas only check structure. Noise, suppression and scope checks are carried out by the
middleware; the policy is the specification it follows.

## Tiers

| | Public | Authenticated | Authorized |
|---|---|---|---|
| Who | Anyone, without signing in | Signed in through NIH RAS | Authenticated, with dbGaP approval for at least one consent group in the release |
| Accountability | None | RAS account | RAS account plus visa IDs |
| Exact counts | Never | Never | Within exact scope: entitled consent groups whose current eligibility allows exact counts |
| Limits | 60 requests per minute per network address | 500 query units per day per account | No budget within exact scope; other queries draw on the authenticated budget. Every request is logged |
| Overlap check | — | Blocks a query whose matched set differs from an earlier one by fewer than `min_count` participants | Not yet decided |
| Retired releases | No | No | Own saved cohorts only |

### Stage by stage

Each cell gives the pool and the profile, then the stage's limits. "No counts" means the stage
has no profile.

| Stage | Public | Authenticated | Authorized |
|---|---|---|---|
| 0 Sign-in and scope | Not available | Sign in; budget assigned | Sign in; exact scope computed from visas and shown up front |
| 1 Search and add terms | `api_search`, no counts. Stigmatizing terms shown, not filterable | `api_search`, no counts. Stigmatizing terms shown, not filterable | `api_search`, no counts. Stigmatizing terms filterable within exact scope, if approved |
| 2 Live summary per term | `api_public` → Totals | `api_public` → Totals | `api_counting` → Exact |
| 3 And, Or and Not | `api_public` → Totals. And only; 5 terms | `api_public` → Totals. And, Or, Not; 20 terms; nesting 3 | `api_counting` → Exact. And, Or, Not; 20 terms; nesting 3 |
| 4 Refine criteria | `api_public` → Totals. Ranges on bin edges only; no time windows | `api_counting` → Totals. Ranges at least one bin wide; time windows of at least 30 days | `api_counting` → Exact. Range minimums relaxed within exact scope, if agreed; time windows |
| 5 Cohort and visuals | Not available | `api_counting` → Breakdown. Obfuscated charts; unreported consent groups listed as below `min_count` | `api_counting` → Exact. Exact charts within exact scope, obfuscated outside it |
| 6 Provisioning | No counts. Information on how to request access | No counts. Access request prefilled from the cohort | No counts. A share for eligible groups, an access request for the rest |

Authenticated stage 4 runs as `api_counting` because value and time criteria need event rows,
but its output is still checked against the public Totals profile.

### What each profile releases

| Profile | Totals | Per-study counts | `record_count` | Used by |
|---|---|---|---|---|
| `TotalsSummaryResponse` | Obfuscated | None; studies at or above `min_count` are listed without counts | Never | Public and authenticated, stages 2–4 |
| `BreakdownSummaryResponse` | Obfuscated | Obfuscated, per study and consent group, each with a `count_status` | Never | Authenticated, stage 5 |
| `ExactSummaryResponse` | Exact within exact scope, obfuscated outside it, as two figures never combined | Exact within exact scope, obfuscated outside it | Only within exact scope | Authorized, stages 2–5 |

`ExactSummaryResponse` is structural only. The middleware must verify the caller's scope before
releasing any exact count.

## How counts are protected

These rules, under `counting`, apply to every tier.

- **Minimum count.** Counts below `min_count` (10) are not reported. `BELOW_MIN_COUNT` means
  "fewer than 10, possibly none", so zero and small counts look alike.
- **Who is counted.** One BDCHM `Participant` is one enrollment, so a person in two studies counts
  twice.
- **Noise.** Obfuscated counts at or above `min_count` get a whole number drawn uniformly from −3
  to +3; a result below `min_count` is shown as `min_count`. The noise is seeded by HMAC-SHA256
  over the release and the matched participants, never the cell's label, so the same participants
  get the same noise wherever they appear. Averaging repeated queries does not remove it.
- **Totals.** A total is the exact union of matched participants across the studies in scope,
  including studies below `min_count`, obfuscated once. It is never a sum of contributions. It is
  exact only if every contributing consent group is in the caller's exact scope. Clients use a
  released total where there is one, and never add up obfuscated counts.
- **Complementary suppression.** Where a parent appears with its parts, the amount a reader could
  work out from the hidden parts must itself be at least `min_count`. Otherwise further parts are
  withheld, smallest first, and if that fails the parent is withheld. Parents include totals over
  their contributions and the cohort total over each facet's values, counting an implied "not
  recorded" part.
- **Releases.** Public and authenticated users query the active release only, and overlap checks
  compare queries across releases.

## Eligibility defaults

The committees decide, for each consent group, whether its participants appear in discovery
counts, whether it can be in an exact scope, and whether its data can be shared at provisioning.
`eligibility` lists suggested starting points for curators, by consent modifier; the committees'
decision per group is what applies.

| Modifier | Discovery counts | Exact counts | Sharing |
|---|---|---|---|
| COL | Allow | Deny | Deny |
| GSO | Review | Deny | Review |
| NPUNCU | Allow | Allow | Review |

Discovery counts as a separate decision is itself proposed.

## Conventions

- **Every stage is written out in full.** Each tier lists all seven stages, and each stage gives
  `available`, `pool` and `profile`. `none` means none, so a missing value is an error, never a
  silent default. An unavailable stage has pool and profile `none` and nothing else.
- **Decisions are fields; meanings are in the schema.** The policy holds values the committees
  can change, such as thresholds, limits and enum choices. What each value means is in the
  descriptions in [`schema/policy.yaml`](../schema/policy.yaml).
- **Versions.** Any change issues a new `policy_version`, including any change to `min_count`.

## What the schema enforces

[`schema/policy.yaml`](../schema/policy.yaml) rejects a policy that would release counts no profile
checks, or that gives a tier more than it should have:

- A stage that returns counts must name a profile; only search may query without one.
- Search never returns counts, and stages 0 and 6 run no queries.
- `api_public` can only produce the Totals profile.
- Public stages can't use `api_counting` and get at most Totals; authenticated stages never get
  Exact.
- Only the authorized tier has an exact scope; the public tier needs a rate limit, and the other
  tiers need a budget.
- Every tier has exactly seven stages, numbered 0 to 6, and there are exactly three tiers.
- Noise can't be seeded by anything except the release and the matched participants.
- Unknown fields are rejected, so prose can't slip back in as an unchecked field.

The tests also check what LinkML rules cannot express: tier names and stage numbers are unique,
unavailable stages are inert, and an approved policy names its noise key (`key_reference`). They also confirm that every profile the policy names exists in
`summary-profiles.yaml`, and that `identity_rule` is a BDCHM class.

## Changing the policy

1. Edit [`disclosure-policy.yaml`](disclosure-policy.yaml) and increase `policy_version`.
2. Run the tests:

   ```sh
   uv run pytest schema/tests/test_disclosure_policy.py
   ```

   The `identity_rule` test needs BDCHM; run `synthetic/fetch-bdchm.sh` once first.
3. If the change needs a new kind of value, such as a new pool, profile or chart mode, add it to
   [`schema/policy.yaml`](../schema/policy.yaml) with a description of what it means.
4. If the change alters what a profile may contain, update
   [`schema/generate_summary_profiles.py`](../schema/generate_summary_profiles.py) and regenerate
   `summary-profiles.yaml`.

## Open questions

- Whether the overlap check applies to authorized users' queries outside their exact scope.
- `ExactSummaryResponse` cannot yet carry the exact and obfuscated figures side by side.
- The Key Vault key for the noise seed (`key_reference`) is not yet named. The tests will fail if
  the policy is approved without it.
- The profile tests use a `min_count` of 11; they should follow the policy's 10.
